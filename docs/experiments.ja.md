# 研究計画

[English](experiments.md) · [ホーム](../README.ja.md) · [エージェントへの指示](../AGENTS.md)

**研究質問**　同じレビュー予算で、AIエージェントにLeanの実行可能な仕様と証明検査器を持たせると、正しい変更を受け入れながら、実務コードの誤った変更をより多く発見できるか。

| 段階 | 実験 | 判定に使うもの |
| --- | --- | --- |
| 0　学んで追試する | 予約仕様を証明し、Python・TypeScriptで同じ入力を動かす。境界条件を間違えた実装も調べる。 | ハーネスを動かせる最初の実例。[初回の成功ログ](https://github.com/moruku36/lean-code-assurance-lab/actions/runs/45159429077) |
| 1　エージェントを比較する | 予約上限、時間枠の端点、再試行の可否など、独立した判定関数3件を選ぶ。各関数に正しい変更と誤った変更を1件ずつ用意する。 | 未使用の6変更を対にして比較し、検出と過剰な拒否を個別に記録する。 |
| 2　既存サービスを1件使う | 担当者がPythonまたはTypeScriptの関数の版を固定し、匿名化した実例と、コードから独立した業務要件を渡す。 | 実関数を別途レビューした仕様と照合する。公開可能な範囲で結果または公開用の合成例を残す。 |
| 3　Rustのソースとつなぐ | オーバーフロー時の挙動を定めた安全な関数をAeneasで変換し、生成物の定理と実ソースの境界例を調べる。 | 変換の対応関係と前提を記録する。非対応なら該当する言語機能を残す。 |
| 4　状態を持つ処理へ広げる | 予約・取消・再試行を遷移として表し、永続化や並行実行を一つずつ追加する。 | 到達可能な状態での不変条件と、その境界を通る実行履歴を記録する。 |

## 最初の比較実験

1. 業務要件、正しい結果、開始時の版、変更可能なファイル、予算を先に固定します。正解ラベルと最終評価用の例は別担当が保管します。誤検出を見るため、正しい変更も含めます。
2. 同じ変更、要件、モデル版、初期テスト、時間・トークン上限を、独立した作業環境のA/Bに渡します。Aは通常のテストを追加・実行でき、Bは加えてLean、実行可能な仕様、証明検査器を使えます。実行順を交互にし、Bのために人が仕様を書いた時間も計上します。
3. 両者の回答を固定してから正解を開きます。変更ごとに、採用・拒否・未判定、正解、追試できる反例や定理、実時間、トークン、人の所要時間、環境障害を記録します。可能なら判定者にはA/Bの名前を伏せます。
4. 片方だけが発見した欠陥、正しい変更を誤って拒否した件数、未判定を、事例とコスト付きで集計します。集計単位は関数または変更です。1関数で大量の入力を試しても、対象関数は1件です。
5. この少数試験は探索用です。Bだけが発見した再現可能な不具合があり、新たな誤判定がなく、事前予算にも収まれば、同じ方式で別の未使用関数に進みます。結果を見て設計を変更した場合、その評価例は開発用に移します。

**仕様そのものにも対照を用意します。** 「受理した予約は定員以下」だけなら、全部拒否する実装でも通ります。「満員ちょうどなら受理」といった正例と、受理が必須となる条件を定理にすると、実装のバグと要件の書き漏れを切り分けられます。
